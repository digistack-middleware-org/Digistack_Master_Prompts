Interview-1 — Project Walkthrough
--------------------------------------
Objective: Explain DigiStack Bank as if you built it in your company —
fluent, confident, unscripted.

Topics
- Enterprise Architecture (ARCH01's logical/application/data/deployment
  views)
- Request Flow (a Fund Transfer, end to end)
- Why WebSphere ND (vs. Tomcat-only, vs. open-source alternatives)
- Why IBM HTTP Server (vs. NGINX-only at the web tier)
- Why CBS (single writer, single EAR, sole-writer rule)
- Why MQ (vs. SIBus alone, vs. no async at all)
- Why PostgreSQL (vs. MySQL/Oracle)
- Deployment Architecture (7 WAS EARs + 2 Tomcat WARs, heterogeneous
  topology behind one IHS/LB tier)
- Design Decisions (the ones this roadmap documented explicitly: CBS
  stays a single EAR, Payment Hub as a Saga not XA, Card Portal on WAS
  not Tomcat, Reporting Service's accepted OLTP-read tradeoff)

Example Questions (answer in your own words, 60–90 seconds each, no
notes)
1. Explain your project architecture, start to finish.
2. Explain what happens when a customer submits a Fund Transfer, from
   browser click to balance update.
3. Why did you separate Portal and CBS instead of keeping one EAR?
4. Why does Payment Hub exist instead of putting NEFT/IMPS logic inside
   CBS?
5. Why does Mobile Banking run on Tomcat instead of WebSphere?
6. Why is Card Portal on WebSphere when Mobile and ATM are on Tomcat?
7. Why does CBS never get split into microservices, even though every
   satellite service is its own EAR?
8. What's the single most important rule in your architecture, and what
   would break if it were violated?
9. Walk me through your database evolution — shared DB → dedicated
   digistack_cbs.
10. What was the hardest architectural decision you had to defend, and
    why did you land where you did?

Model-Answer Skeleton (use this shape for every "why" question)
State the decision plainly (one sentence).
State the alternative(s) considered.
State the concrete tradeoff — what you gained, what you gave up.
Tie it back to a real constraint (P-2/P-5, single-writer rule,
lab-scale realism, WebSphere-practice-first filter).
Example, applied to Q5 (Why Tomcat for Mobile):
"Mobile and ATM are genuinely external, lower-risk customer channels, so
I deliberately kept them off the WAS cluster and put them on Tomcat
instead. The alternative was deploying them as WAS EARs like everything
else, but that would've just been more of the same admin practice I was
already getting from 7 other EARs — the actual value was in configuring
IHS to route two different subdomains to two completely different
backend server types, which is real heterogeneous-topology work. Card
Portal is the deliberate counterpoint — it handles sensitive card
lifecycle operations, so I treated it as a bank-owned enterprise app and
kept it on WAS, which is also the more realistic real-world pattern."

Sprint Deliverable: Candidate delivers a 5-minute unscripted project
walkthrough (recorded or live to an interviewer/peer) covering
architecture, one request flow in detail, and at least three "why"
decisions — no slides, no notes.

Interview-4 — Troubleshooting
------------------------------------
Objective: Handle real production scenarios under pressure, using a
consistent diagnostic shape for every incident type.

Standard Shape (apply to every scenario below)

Symptoms → Logs → Root Cause → Investigation → Resolution → Prevention


Scenarios (minimum set — each must be worked through the full shape
above, not just named)

1. **Node Agent Down**
   - Symptoms: DMgr can't reach node; node's servers show unknown status.
   - Logs: nodeagent's SystemOut.log, DMgr's SystemOut.log.
   - Investigation: process check, port check, node sync status.
   - Resolution: restart Node Agent, re-sync if config drifted.
   - Prevention: monitoring alert on Node Agent process health.

2. **DMgr Down**
   - Symptoms: Admin Console unreachable; cluster members keep running
     (DMgr isn't in the runtime request path).
   - Investigation: DMgr process/log check, disk space, profile
     corruption.
   - Resolution: restart DMgr; restore from backupConfig if corrupted.
   - Prevention: DMgr health monitoring, profile backup cadence.

3. **Cluster Down**
   - Symptoms: all cluster members unreachable; total application
     outage.
   - Investigation: check each member individually, check IHS/plugin
     routing, check underlying DB/network.
   - Resolution: staged restart, member by member; confirm session
     failover during restart per P05 v36 discipline.
   - Prevention: HA drills (P05 v36), alerting on member count dropping.

4. **JDBC Pool Exhausted**
   - Symptoms: application hangs/errors on DB calls; pool wait-time
     metric spikes.
   - Investigation: check for connection leaks, long-running queries,
     pool sizing vs. actual concurrency (P01 v7's math).
   - Resolution: kill leaking connections/restart JVM if leak confirmed;
     resize pool if genuinely undersized.
   - Prevention: connection leak detection, pool monitoring/alerting
     (P04 v31/v34).

5. **Hung Threads**
   - Symptoms: requests stall; thread pool exhaustion warnings in logs.
   - Investigation: thread dump analysis, identify blocked thread's
     stack trace, correlate to a specific service call.
   - Resolution: isolate and fix the blocking call; restart affected
     JVM if unresolvable live.
   - Prevention: timeout enforcement on every external call (ARCH02 §6),
     hung-thread detection policy.

6. **OutOfMemoryError**
   - Symptoms: JVM crashes or becomes unresponsive; heap usage graph
     shows steady climb with no GC recovery.
   - Investigation: heap dump analysis, identify leak source (P01 v14's
     large-report scenario is the canonical example).
   - Resolution: restart JVM; fix the leak/oversized allocation at the
     code or config level.
   - Prevention: heap sizing discipline, load testing before rollout
     (P04 v33).

7. **Session Loss**
   - Symptoms: users unexpectedly logged out / cart or form state lost.
   - Investigation: confirm session replication config, check if
     failover actually occurred vs. a true bug.
   - Resolution: fix replication config; if isolated, may be a
     legitimate timeout (P01 v9).
   - Prevention: session-failover drills (P05 v36 Scenario B).

8. **MQ Queue Full**
   - Symptoms: producer errors/backpressure; queue depth alert fires.
   - Investigation: check consumer health (is the MDB/listener down?),
     check for a downstream outage backing up the queue.
   - Resolution: restart stalled consumer; drain queue once fixed.
   - Prevention: queue depth alerting (P04 v34), DLQ monitoring.

9. **SSL Failure**
   - Symptoms: handshake errors; certain hops fail while others work.
   - Investigation: check cert expiry, keystore/truststore mismatch,
     cipher suite mismatch.
   - Resolution: renew/re-import cert; align keystore config.
   - Prevention: certificate expiry tracking (doc 07 §7 Certificate
     Inventory).

10. **Plugin Failure**
    - Symptoms: IHS returns errors even though WAS cluster is healthy.
    - Investigation: check plugin-cfg.xml for staleness vs. current
      cluster membership.
    - Resolution: regenerate and propagate plugin.
    - Prevention: automate plugin regen on cluster membership change
      (P05 v36, P08 v52).

11. **Deployment Failure**
    - Symptoms: EAR fails to start post-deploy; app shows red in Admin
      Console.
    - Investigation: check SystemOut/FFDC for the specific startup
      exception, check JNDI resource resolution.
    - Resolution: rollback to previous version (P01 v4 discipline);
      fix and redeploy.
    - Prevention: smoke test gating before promotion (doc 04, P08 v52).

12. **Database Down**
    - Symptoms: total application failure on any DB-backed operation.
    - Investigation: confirm DB process/network reachability, check for
      failover in progress (P05 v38).
    - Resolution: wait for automatic recovery or manually promote
      standby; confirm connection pool recovers cleanly.
    - Prevention: DB HA/replication (P05 v38), JDBC failover validation.

Sprint Deliverable: Candidate is given 3 scenarios at random (not
pre-announced) and must talk through the full Symptoms → Prevention
shape out loud within 5 minutes each, as if paged at 2 AM.

Interview-5 — Banking Production Environment
--------------------------------------------------
Objective: Speak convincingly about the banking domain itself, not just
the infrastructure underneath it.

Topics
NEFT, IMPS, asynchronous processing rationale, CBS rationale, BOD/EOD,
Payment Hub, DR, Multi-region.

Example Questions & Answer Anchors
1. **How does NEFT work?** Batch-window settlement — transfers are
   accumulated and processed in scheduled batches rather than real-time,
   which is why P03 v25 models it as a batch job rather than a
   synchronous call.
2. **How does IMPS work?** Real-time settlement — synchronous validation
   with async confirmation, available 24/7, which is why v25 gives it
   the JMS/MQ real-time path instead of a batch window.
3. **Why MQ instead of just calling CBS directly for payments?**
   Decouples Payment Hub's availability from CBS's — a payment can be
   accepted and queued even if CBS is briefly unavailable, and MQ's
   persistence guarantees the message isn't lost (P05 v38's MQ
   continuity scenario).
4. **Why asynchronous processing for Fund Transfer at all?** Lets the
   customer get an immediate "accepted" response while the actual
   balance update happens reliably in the background — better perceived
   performance without sacrificing correctness (P02 v15's original
   rationale).
5. **Why does CBS exist as a single system of record instead of each
   channel having its own database?** One authoritative writer avoids
   split-brain balance data — every channel becomes a thin client to
   one truth (ARCH01 P-2).
6. **Explain BOD/EOD.** Beginning/End of Day batch windows — BOD opens
   the banking day (e.g., interest accrual prep, NEFT batch window
   opens); EOD closes it and reconciles the day's settlements against
   CBS's ledger (P03 v29).
7. **Explain Payment Hub's role precisely.** Routes and coordinates
   payments but never writes balances directly — settlement is
   confirmed back to CBS, which alone performs the write; this is a
   Saga pattern, deliberately avoiding a distributed XA transaction
   across independently deployed EARs (P03 v25).
8. **Explain your DR setup.** Primary/Secondary site pairing (Hyderabad
   ↔ Bangalore, P05 v37) with streaming DB replication and defined
   RPO/RTO per flow — Fund Transfer at 0 min RPO / 15 min RTO, reporting
   at a much looser bar since it can be regenerated.
9. **Explain multi-region.** Independent regional deployments (India/
   Singapore/Dubai, P06 v39) each authoritative for their own region's
   customer data, with GSLB routing and mTLS-secured cross-region calls
   only where genuinely needed (v41) — not one global replicated
   customer table.
10. **Why is Reporting Service allowed to read the OLTP database
    directly when nothing else is?** An explicitly documented, accepted
    tradeoff (ARCH01 §Risks) — avoided introducing new read-replica
    infrastructure mid-build; closed later at P09 v64's RDS read
    replica.

Sprint Deliverable: Candidate answers 10 domain questions (drawn from
this list or equivalent) without infrastructure jargon creeping in where
a business-level answer is expected — practice distinguishing "how the
platform does it" from "why the bank needs it."
