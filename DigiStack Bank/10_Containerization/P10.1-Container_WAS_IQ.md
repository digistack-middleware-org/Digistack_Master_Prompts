Purpose
-------
Same discipline as P03.2/P07.1/P08.1/P09.1, one final tier up: a
permanent, fully-worked interview reference book derived entirely from
P10 — every question, scenario, troubleshooting case, runbook, and mock
interview must map back to a specific version actually built in that
Part. P10 covers Containerization Foundations, Kubernetes/EKS
Orchestration, Container Networking & Service Mesh, Container CI/CD &
GitOps, and the Containerization Capstone — this file is the interview
material for exactly that, nothing else.

Boundary Note (P10.1 vs. prior Interview Parts)
------------------------------------------------------
- P03.2 — the application itself (CBS, Fund Transfer, channel simulators).
- P07.1 — operating/recovering/scaling/migrating that application
  on-prem (observability, HA/DR, multi-region, WAS platform migration).
- P08.1 — how the application/platform gets built, tested, and deployed
  (Git, CI/CD, IaC, deployment automation).
- P09.1 — how the same unchanged application moves onto AWS (hybrid
  connectivity, lift-and-shift, managed-service modernization, cutover).
- P10.1 — how that AWS-native platform gets repackaged into containers
  and orchestrated (Docker, EKS, service mesh, GitOps). A question about
  Kubernetes readiness/liveness probes belongs here; a question about
  RDS Multi-AZ failover belongs in P09.1; a question about what Fund
  Transfer does belongs in P03.2.

Deployment Model
------------------
Zero new banking functionality, zero new infrastructure — documentation/
reference artifacts only, same as every prior Interview Part. Produced
sprint by sprint, one chapter's worth of content at a time, in the agreed
format: short spoken-style answer + why-it's-asked + implementation
reference + architecture tie-in + real example + follow-ups + mistakes +
best practices.

Placement Note
------------------
Suffix Part, same mechanism as P03.1/P03.2/P07.1/P08.1/P09.1. Sits after
P10 in reading order (P10 → P10.1). No version numbers (v1–v78) are
touched; this produces no deployables. This is currently the final
Interview Part in the roadmap, mirroring P10 being the final versioned
Part — no further Interview Part is scoped or implied beyond this one
unless a future, explicitly new Part is proposed.

Prerequisite
------------------
P10 Completion Checkpoint satisfied — all 9 applications containerized
and running as Kubernetes Deployments on EKS, service mesh mTLS
confirmed, GitOps (Argo CD/Flux + Helm) as the sole deployment path,
part10-release tag applied, EC2-hosted WebSphere estate decommissioned.
Assumes the candidate actually built P10, not merely read about it, same
standing assumption every prior Interview Part makes.

------------------------------------------------------------

foundations, Kubernetes orchestration, networking/service mesh, and
GitOps, each fully worked in the agreed format.

Sprint 1 — Containerization Foundations (P10 v74)
(Dockerfile/multi-stage builds, WAS traditional vs. Open Liberty base
image decision, ECR immutable tagging, container HEALTHCHECK reusing
P04 v31's /health endpoint, JVM heap tuning under cgroup limits)

Sprint 2 — Kubernetes / EKS Orchestration (P10 v75)
(Pods/Deployments/Services, ConfigMaps/Secrets via Secrets Store CSI
Driver, readiness vs. liveness probes, HPA as the container-native

placement constraint under Kubernetes)

Sprint 3 — Container Networking & Service Mesh (P10 v76)
(CNI/Ingress replacing IHS's external-facing role, Network Policies
re-enforcing the single-writer rule, service mesh mTLS as the
container-native continuation of P01 v12/P06 v41, circuit breaking vs.
Payment Hub's existing retry policy)

Sprint 4 — Container CI/CD & GitOps (P10 v77)
(image build/scan/publish extending P08 v50's Nexus step, Argo CD/Flux
declarative reconciliation vs. imperative kubectl, Helm charts as the
container-native equivalent of P08 v51's Ansible group_vars, canary
rollout via service mesh)

Sprint 5 — Cross-Cutting Container Concerns
(WebSphere-inside-a-container tradeoffs, why WAS traditional was
retained instead of Open Liberty, cost/complexity of running a stateful
singleton like the Messaging Engine on a stateless orchestration
platform)

Sprint 6 — Capstone: Containerization Capstone (P10 v78)
(Migration Success Criteria shape reused from P07 v48/P09 v73, full
regression against the containerized platform, observability extension

agreed short-answer format.

Version 2 — Chapter 2: Real Production Scenarios
------------------------------------------------------------
Objective: Realistic production scenarios built from P10 components
(Docker/ECR, EKS, Ingress/service mesh, Argo CD/Flux, Helm).

Sprint 1 — Container Build/Image Scenarios (image vulnerability found
post-publish, base image drift between build and runtime stage)
Sprint 2 — Orchestration Scenarios (pod eviction losing session state
unexpectedly, HPA scaling the wrong Deployment under load, ConfigMap
update not picked up without a rolling restart)
Sprint 3 — Messaging-Engine-Under-Kubernetes Scenarios (SIBus ME pinned
replica accidentally scaled by HPA, ME failover behaving differently
than P05 v36's VM-based drill)
Sprint 4 — Networking/Mesh Scenarios (Network Policy accidentally
blocking a legitimate satellite-service call, mesh mTLS misconfiguration
silently failing open instead of closed)
Sprint 5 — GitOps Scenarios (Argo CD reconciliation loop fighting a
manual kubectl change, canary rollout stuck at partial traffic)
Sprint 6 — Capstone: Combined scenario — a GitOps-driven rollout
triggers a Network Policy conflict that also affects the pinned
Messaging Engine pod

Deliverable: Full scenario bank, each tied to a specific component and a
specific P10 version.

Version 3 — Chapter 3: Production Troubleshooting
------------------------------------------------------------
Objective: Full troubleshooting cases in the fixed shape: Production
Problem → Business Impact → Symptoms → Request Flow → Components
Involved → Logs to Check → Commands to Execute → Investigation Process →
Root Cause → Resolution → Prevention → Lessons Learned.

Sprint 1 — Image/Build Failures (failed HEALTHCHECK on startup, image
pull failure from ECR)
Sprint 2 — Orchestration Failures (CrashLoopBackOff on a WAS pod, HPA
not scaling despite sustained load, readiness probe flapping)
Sprint 3 — Stateful Workload Failures (Messaging Engine unavailable
after a pod reschedule, session data lost despite prior replication
guarantees)
Sprint 4 — Networking/Mesh Failures (mTLS handshake failure between
mesh sidecars, Ingress TLS termination misconfiguration)
Sprint 5 — GitOps Failures (Argo CD out-of-sync state not
auto-reconciling, Helm chart value drift between environments)
Sprint 6 — Capstone: Full-stack containerized incident — orchestration
+ networking + GitOps failure occurring together

Deliverable: Full troubleshooting case bank, cross-referenced against
P10's own Completion Checklist and Migration Success Criteria.
